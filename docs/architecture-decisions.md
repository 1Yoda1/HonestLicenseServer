# Архитектурные решения перед интеграцией HonestFlow

Дата фиксации: 2026-08-10.

## Граница системы

- HonestLicenseServer хранит авторизацию, клиентов, устройства, заявки, конфигурацию,
  версии, overrides, лицензии и метаданные файлов.
- Исполняемые файлы, установщики и архивы (`.exe`, `.msi`, `.zip`) остаются во
  внешнем приватном объектном хранилище Cloud.ru. Диагностика размещается под
  `diagnostics/` и удаляется через 48 часов; постоянные дистрибутивы — под
  `releases/`. API сохраняет только object key, подписанные метаданные и историю.
- Ключи объектного хранилища не передаются HonestFlow или HonestDesk. API выдаёт
  короткоживущие подписанные URL; бинарные данные не проходят через API.
- Production-база `/opt/honestserver/HonestLicenseFull.db` не входит в publish и
  никогда не заменяется при деплое.

## Устройство и регистрация

- `deviceId` — случайный GUID установки HonestFlow, сохранённый в
  `C:\ProgramData\HonestFlow\device.json`.
- Успешный login с неизвестным `deviceId` автоматически создаёт одну заявку
  `Pending` без дубликатов.
- Pending-устройство получает ограниченную access/refresh-сессию. Она разрешает
  проверять заявку, обновлять сессию, выходить и обращаться в поддержку.
- Рабочая конфигурация и лицензия доступны только активному устройству.
- `Devices.Address` означает физический адрес торговой точки, а не IP-адрес.
- Поддерживаемые архитектуры: `x86`, `x64`, `arm64`.
- Клиенты и устройства отключаются без физического удаления данных.
- `Disabled` Device остаётся известным запрещённым устройством. `Deleted` Device
  считается удалённой регистрацией и может пройти повторную регистрацию; при
  Approve переиспользуется существующая строка Device и сохраняется её история.

## Версии и файлы

- Для версии компонента явно хранятся `Component`, `Version`, `FileName`,
  `DownloadPath`, `Sha256` и `SizeBytes`.
- Клиентский override выбирает версию. Имя и остальные метаданные берутся из
  каталога выбранной версии.
- Эффективная версия: `overrideVersion ?? globalVersion`.
- Публичный `GET /api/version/current/{application}` сохраняется.
- Защищённый `GET /api/configuration/current` возвращает клиенту, устройству и
  effective assets одним запросом.
- При необходимости `GET /api/assets/{component}/download` отвечает `302` на
  короткоживущую подписанную GET-ссылку Cloud.ru; бинарные данные не проходят
  через API. Старые прямые и Яндекс-ссылки читаются только на время миграции.
- Новый дистрибутив подписывается отдельным офлайн ECDSA P-256 ключом. Загружающий
  компьютер вычисляет SHA-256, подписывает манифест и отправляет файл напрямую в
  Cloud.ru multipart-частями. Сервер проверяет подпись паспорта, выдаёт временные
  URL частей, завершает multipart-сессию и через `HEAD` проверяет только размер;
  содержимое дистрибутива через сервер не проходит. HonestFlow сверяет подписанный
  SHA-256 после скачивания до запуска файла.
- Сайт использует постоянный публичный `GET /api/downloads/honestflow/setup`.
  Маршрут выбирает текущий подписанный `HonestFlowInstaller` и перенаправляет на
  короткоживущую GET-ссылку Cloud.ru; адрес объекта и секреты бакета в HTML не
  публикуются.
  Закрытый ключ выпуска отсутствует на сервере, в HonestFlow и в Git.
- Диагностика загружается HonestFlow напрямую в приватный S3-бакет по
  подписанному PUT URL. HonestDesk скачивает её напрямую по подписанному GET URL.
  ZIP удаляется по команде HonestDesk либо автоматически через 48 часов;
  запись `DiagnosticArchives` остаётся в SQLite со статусом `Deleted`/`Expired`.

## Лицензия и ECDSA

- Закрытый ECDSA-ключ существует только в HonestDesk.
- Публичный ключ встроен в HonestFlow и отдельно настроен на сервере.
- Сервер проверяет подпись при публикации лицензии и поддерживает ротацию через
  `keyId`.
- Публичный ключ задаётся на сервере как SubjectPublicKeyInfo Base64, например
  `LicenseSigningKeys__primary-2026__PublicKeyBase64`. Закрытый ключ в конфигурации
  сервера отсутствует.
- Исходные подписанные grant-байты хранятся как BLOB и не сериализуются повторно.
- Старый формат подписывает целиком `licenses.json`; его DER-подпись нельзя
  переносить на извлечённые персональные JSON. Такие импортированные строки имеют
  `SignatureScope = LegacySnapshot` и не выдаются как персональные grants.
- Новые лицензии имеют `SignatureScope = PersonalGrant` и выдаются только после
  успешной серверной проверки подписи.
- Для пары client/device существует одна текущая лицензия; предыдущие ревизии
  сохраняются как история (`Superseded`, `Revoked`, `Expired`).
- HonestFlow кэширует исходный grant и подпись, проверяет ECDSA локально и может
  работать offline только до подписанного `validUntilUtc`.
- `LicensePolicies.IsEnabled` — единственный административный source of truth
  для client-level доступа HonestFlow при online startup.
- `ClientEnabled` остаётся внутри подписанного grant как совместимый offline/legacy
  snapshot и при новой публикации автоматически вычисляется из
  `LicensePolicies.IsEnabled` (`null` означает legacy allow). Это не отдельный
  административный переключатель.
- Device entitlement, features, срок действия, offline grace и остальные
  device-level ограничения остаются внутри подписанного grant.

## Отложено

- Самостоятельная смена пароля.
- «Выйти со всех устройств».
- Уведомления Max для заявок подключения и обращений поддержки. Сервер сохраняет
  текстовые обращения в `SupportRequests` и возвращает `202 Accepted`.
- Интеграция HonestFlow и HonestDesk выполняется после стабилизации и тестирования
  серверного API.
- C#-клиент генерируется NSwag после стабилизации OpenAPI-контракта.

## Заявки подключения сайта (2026-11-04)

- Заявка сохраняется в `ConnectionRequests`; SMTP исключён из приёма и конфигурации.
- HonestDesk получает заявки через защищённый admin API и меняет серверный статус
  (`New`, `InProgress`, `Completed`, `Rejected`), включая возврат в новые.
- Изменение статуса защищено проверкой `expectedStatus` и записывается в аудит
  в одной транзакции. Клиент не подменяет подтверждение сервера локальным флагом.
- Старые поля почтовой доставки сохраняются до уничтожения соответствующей заявки.
- Max будет отдельным каналом уведомлений о заявках подключения и запросах помощи.
  Приём и хранение обращений не должны зависеть от доступности мессенджера.
## Уничтожение персональных данных заявок (2026-11-04)

- Новые, отклонённые и завершённые заявки удаляются физически в пределах 30 суток в текущем статусе (опрос начинает удаление на один интервал раньше).
  Время хранится в `ConnectionRequests.StatusChangedAtUtc`, старые значения
  восстанавливаются из аудита либо даты создания без перезаписи существующих дат.
- HonestDesk может безвозвратно удалить заявку любого статуса через admin DELETE.
  Заявка и её аудит удаляются одной транзакцией, без сохранения идентификаторов,
  IP, контактов и текста в новом событии удаления. Остальные сущности не удаляются.
- Удаление использует `secure_delete=ON` и проверяемый `wal_checkpoint(TRUNCATE)`.
  Незавершённая очистка WAL не выдаётся за успешное уничтожение; фоновая очистка
  повторяется каждые 15 минут, начиная со старта API.
- Правило soft-delete для Clients/Devices сохраняется. Это исключение касается
  только явно запрошенного уничтожения ConnectionRequests.
- Рабочая база не равна резервным копиям и внешним журналам. Их уничтожение и
  предотвращение возврата удалённых ПД при восстановлении требуют отдельного
  регламента. Механизм Max в эту задачу не входит.

## Документы сайта v1.0 (подготовка, без включения production)

- Канонические Markdown политики и отдельного согласия находятся в
  `Documents/Privacy/v1.0/`, встроены как ресурсы и совпадают с файлами владельца.
- Единственная страница документа — существующая `/privacy/`; согласие находится
  в раскрытии непосредственно в форме. Тексты статические и не зависят от
  доступности приёма. Версия формы, серверной проверки и доказательства — `1.0`.
- Для приёма нужны одновременно Enabled и явное ApprovedDocumentVersion=1.0.
  Значения по умолчанию запрещают приём, PreContract больше не допускается для
  этой редакции. Изменение не затрагивает лицензирование и другие формы.
- Completed тоже подлежит удалению: прежний алгоритм New/Rejected расходился с
  пунктом 5.1 политики. Отдельные договорные записи в этот процесс не входят.
- География БД/бэкапов, хранение журналов, исполнение обращений по email и
  обязательные действия оператора не подтверждаются исходным кодом; до их
  завершения и утверждения владельцем приём остаётся закрытым.
